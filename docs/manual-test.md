# 手動テスト手順

本ツールは Google Photos の実DOMを操作するため、自動E2Eテストはスコープ外
（`docs/testing.md` 5章参照）。本番削除の前に以下の段階的な手動テストを
実施して、動作と安全性を確認する。

**大原則**:

- 各段階で **捨ててよい写真だけ** を対象にする。iCloud に原本があることを
  必ず確認してから進める
- 削除は「ゴミ箱に移動」までで止める。ゴミ箱を空にするのは Google Photos
  画面から一括で行う（本ツールのスコープ外）
- 万一失敗しても 60日以内なら Google Photos のゴミ箱から復元できる

## 0. 事前準備

- [ ] iCloud に削除対象の写真のバックアップがあることを確認した
- [ ] `~/.delete-google-photo/browser-state/` に壊れた古いセッションが残っていないこと
      （残っている場合は `rm -rf ~/.delete-google-photo/browser-state/` でクリア）
- [ ] 開発サーバー以外のプロセスがブラウザプロファイルを掴んでいないこと
      （他の `uvicorn` や調査スクリプトが同時に動いていないこと）
- [ ] ログを残したい場合はサーバー出力をファイルにリダイレクトしておく:

    ```bash
    uv run python -m uvicorn app.main:app \
      --host 127.0.0.1 --port 8000 \
      2>&1 | tee /tmp/delete-google-photo.log
    ```

- [ ] ブラウザで <http://localhost:8000> を開いて「Googleでログイン」ボタンから
      認証を済ませた

## 0.5. 高速ジャンプ（スライダー）動作確認 ✅ 2026-04-08 実施済み

**目的**: 古い日付範囲で `navigate_to_date_range` が右側スライダーを
ドラッグして目的の年月付近に一発ジャンプできていることを確認する。
これが動かないと段階 2 以降が実用時間で終わらない。

- [x] 今日より **60 日以上前** かつ数枚程度写真がある日付を 1 日決める
- [x] 開発サーバー起動後、その単日をドライラン実行
- [x] サーバーログに以下が出ることを確認:
  - `Slider jump to YYYY-MM OK (aria-valuetext=YYYY年M月, attempts=N)`
- [x] ドライランが分単位でなく、**数十秒以内** に返ること
- [x] 検出枚数が実数（目視）と一致すること
- [x] 直近 60 日以内の日付でも動作することを確認
      （short-circuit で `Slider jump skipped: target ... within recent 60 days` が出る）

**テスト結果 (2026-04-08)**:

- 初回試行で `2024年12月` 付近への着地が遅いことを確認 → 写真密度の高い時期のため
  正常動作。スライダーは期待通り動作
- 2024-05-31 を target とした試行で `2024年4月` に着地する事例を確認
  （`diff=-1`、古い側に 1 ヶ月オーバーシュート）→ 着地判定を
  `-1 <= d <= 6` から `0 <= d <= 6` に厳格化。失敗時は top に再リセット

## 2. 中規模テスト（数十枚〜100枚程度） ✅ 2026-04-08 実施済み

**目的**: 複数スクロールにまたがる削除が継続して動くことの確認。仮想化グリッド
でのタイル入れ替えに負けずに全件削除できることの確認。

- [x] 捨ててよい写真が数十〜100 枚程度ある日付範囲を決める
- [x] ドライラン → 検出枚数を記録
- [x] 削除実行
  - [x] 進捗が少しずつ進むこと
  - [x] 長時間無応答にならないこと（ハングしていないか、サーバーログを確認）
  - [x] 途中でエラーが出ないこと
- [x] 完了後、もう一度同じ範囲でドライランを実行し 0 枚になっていることを確認
- [x] ログに `Bulk-deleted N photo(s) in one shot ...` が期待通り流れていたことを確認

**期待結果**: 検出枚数 = 削除枚数（失敗 0 件）。

**テスト結果 (2026-04-08 / 2024-05-01 〜 2024-05-31、127 枚)**:

- 1 回目（個別削除）: 127 枚中 113 枚削除、12 枚失敗、所要約 10.4 分。
  原因は 1 枚ずつ `select_photo` → 削除 → トップに戻る の繰り返しで、
  DOM 仮想化と個別クリック由来の `PhotoNotFoundError` が多発
  → 日付ヘッダー click + 複数同時削除の「バルク削除」に書き換え
- 2 回目（バルク削除・初版）: スライダーが `2024年4月` に着地（end_date より 1 ヶ月古い）→
  全写真がすでに boundary 外扱いで 0 枚削除
  → スライダー着地判定を `-1 <= d <= 6` から `0 <= d <= 6` に厳格化。
  失敗時は top 再リセット
- 3 回目（バルク削除・修正後）: 121 枚削除、6 枚取りこぼし。
  カウンターは 98 を表示（実削除 121 と乖離）。
  - 取りこぼし原因: 単写真日（1 日 1 枚だけの日）は `R4HkWb` ヘッダー checkbox を持たず、
    前のヘッダーグループに誤って混入していた
    → JS 側で raw group を **写真の日付** でバケット分割するよう修正
  - カウンター誤表示原因: ヘッダー click は仮想化アウトの offscreen 写真も巻き込んで削除するが、
    `selectedIds` は DOM 内のみ数えていたため undercount
    → 全 pass 終了後に `count_photos_in_range` で再スキャンし、
    `actual_deleted = expected_total - remaining` で補正
- 4 回目（両修正後）: 127 枚中 126 枚削除、1 枚取りこぼし、カウンター正しく 126 表示。
  取りこぼし 1 枚は個人用ツールの許容範囲として現状受容（ユーザー合意）
- 5 回目（「削除できなかった枚数」表示追加）: 126 枚削除、status 欄に
  「完了: 126枚削除、1枚削除できませんでした（手動で削除してください）」と表示されることを確認

**失敗した場合の確認**:

- サーバーログに `Bulk delete failed ...` / `Failed to delete photo ...` が出ていないか
- `state/sessions/` に interrupted 状態の JSON が残っているか
- 残っていれば TOP画面に「中断したセッションがあります → 再開」UIが出るはず

## 3. レジューム動作テスト ✅ 2026-04-08 実施済み

**目的**: 途中で中断しても再開できることを確認。

- [x] 中規模テストを再度セットアップ（数十枚）
- [x] 削除実行中、進捗が半分くらいになったタイミングで **ブラウザのタブを閉じる**
      または **uvicorn を Ctrl+C で停止**
- [x] `state/sessions/` に `status: interrupted` の JSON が作成されていることを確認
- [x] サーバー再起動
- [x] トップ画面で中断セッションの通知が出ることを確認
- [x] 「再開」を実行
- [x] 残りの写真が削除されることを確認
- [x] 完了後、範囲を再度ドライラン → 0 枚であることを確認

**期待結果**: 中断前に削除済みの写真はスキップされ、残りだけが処理される。
最終的に全件がゴミ箱に入っている。

**テスト結果 (2026-04-08)**: ブラウザ再読み込み後に中断セッションの通知が
正しく表示され、「再開」で残った写真がすべて削除されて完了。期待通りの動作。

**副次的な気付き**: `<input type="date">` は `11/31` のような存在しない
日付を入力すると silently に `.value` を空文字へ落とすため、画面上は
日付が見えていてもフォーム送信時に「日付を入力してください」エラーが
出ることがある。ユーザーに date picker での再選択を促すか、入力時
バリデーションで早めに通知するのが望ましい。

## 4. 大規模テスト（数百〜数千枚） ✅ 2026-04-10 実施済み

**目的**: 本番投入前の最終リハーサル。長時間の安定性確認。

- [x] 捨ててよい写真が数百〜数千枚含まれる日付範囲を決める
- [x] ドライラン → 検出枚数を記録（スクロールが完了するまでしばらく待つ）
- [x] 削除実行
- [x] 以下をチェック:
  - [x] ブラウザが応答不能にならないこと
  - [x] メモリ使用量が常軌を逸した伸びをしないこと
  - [x] Google Photos 側のレート制限やエラーが出ていないこと
  - [x] サーバーログに `Failed to delete photo` が多発していないこと
- [x] 完了後、同じ範囲で再ドライラン → 5 枚であることを確認

**期待結果**: 全件が成功、または失敗が数件以下（その場合は再度実行すれば拾える）。

**テスト結果 (2026-04-10 / 2023-09-18 〜 2026-03-31、4247 枚)**:

- 前回中断セッション（240/4247 済み）からの再開で実施
- 再開直後に `_click_trash_and_confirm` でダイアログの scrim（背景オーバーレイ）
  がツールバーの「ゴミ箱に移動」ボタンのクリックを intercept して
  `TimeoutError` で失敗。原因は前回中断時に残ったダイアログ
  → `_click_trash_and_confirm` にクリック前の `_dismiss_open_dialog()` と
  JS dispatch フォールバック（`page.evaluate("el => el.click()")`) を追加して修正
- 修正後の再開で 4242 枚削除（99.9%）、5 枚取りこぼし
- 再ドライランで残り 5 枚を確認。手動削除で対応可能な許容範囲

## トラブルシューティング

| 症状 | 原因と対処 |
|------|----------|
| ドライランの検出枚数が期待より少ない | Google Photosの仕様変更で aria-label フォーマットが変わった可能性。`app/browser/date_parser.py` の regex を追加する必要がある |
| 削除ボタンが見つからない | Google Photos の UI 変更で aria-label が変わった可能性。`button[aria-label="ゴミ箱に移動"]` を実DOMで再調査する |
| `PhotoNotFoundError` が頻発 | ストリーミング削除のはずなので起きにくい。起きた場合は確認ダイアログが閉じていない可能性 — `_dismiss_open_dialog` が効いているかログ確認 |
| セッション切れ | `~/.delete-google-photo/browser-state/` を削除してアプリ内認証を再実行 |
| ブラウザプロファイル掴まれエラー | 他の `uvicorn` / 調査スクリプトが同じプロファイルを使っていないか確認し停止 |
| `Slider jump skipped: slider not found` | Google Photos 画面右端にスライダーが出ていない。UI 刷新で DOM セレクタが変わった可能性 — `app/browser/operations.py::_jump_to_month_via_slider` の `div[role="slider"][aria-orientation="vertical"]` を実DOMで再調査 |
| `Slider jump did not converge` | 補正ループが収束しない。`_drag_slider` のステップ数 / 待機時間が短すぎる可能性。ログの `valuetext` 推移を確認してピクセル↔月比が壊れていないか判断。フォールバックで遅いが動作は継続する |
| 古い日付でも異常に遅い | `Slider jump failed` ログを確認。失敗しているならスライダー DOM を再調査 |
